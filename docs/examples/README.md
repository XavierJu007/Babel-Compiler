## 表达目标

参考按退款准入、执行依赖、全局约束组织。流程用关系链呈现；并发锁、库存不可用、发票作废、渠道终态错误和对账差异分别绑定到相关动作，不再单独复刻原来的六个章节。`role`、`goal`、`if` 是公开词；业务实体继续使用准确的中文名称，不需要图例或私有映射。

`≤99元→一线客服可直接处理,no approval` 保留“可以处理”和“无需审批”。`no approval`、`No审批` 可在这一上下文表达免审批，不能被读成“禁止审批”；其他金额档的“须审批”仍是义务。`运费可退仅if商家责任` 保留必要条件方向，没有改成“商家责任就必须退运费”。`∧`、`∨`、`∀`、`∃`、`∈`、`∉` 按公共含义使用；不为凑符号而添加因果、双向条件或空集结论。

原文没有解决的问题继续保留：99 元与 500 元的审批区间重叠；子 SKU 失败后先等整单回滚成功、再重试的特殊次序；“已拆封、已激活”的并列关系及部分并列动作的时限作用域。参考不补优先级、不替用户修 SOP。截图要求仍是打码手机号、地址和订单号后 6 位；写操作同时保留前、后状态快照。

## mixed 标签与符号的实际成本

以下分别测量每个独立片段，斜杠两侧的数值对应同一行的片段顺序。

| `角色:` / `role:` | 3 / 2 | 2 / 2 |
| `目标` / `goal` | 2 / 1 | 1 / 1 |
| `目标:` / `goal:` | 3 / 2 | 2 / 2 |
| `无需审批` / `No审批` / `no approval` | 5 / 4 / 2 | 2 / 2 / 2 |

`role`、`goal` 在这两种编码下不比相应中文标签贵；参考选择的 `no approval` 在 `cl100k_base` 下比另外两种免审批表述更短。选择仍取决于完整候选及上下文，不能把片段收益简单相加，也不强制每次用同一种写法。

| 完整片段 | `cl100k_base` | `o200k_base` |

条件片段与因果片段分开比较，`if` 不会把假设变成已发生的原因。实测表明，换成符号不一定更省；默认应主动压缩关系和重复作用域，再按实际编码检查完整候选，而不是机械把每个中文连接词替换成符号。
