# 语义校验与独立盲读

Babel 提供两种校验方式。**默认方式是 `compare`；`blind` 需要显式选择。** 校验方式与是否开启校验是两个选项：CLI 和 `/api/compile` 默认只生成候选，Web 默认勾选「严格校验」，代理始终执行严格校验。

| 方式 | 模型看到什么 | 用途 |
| --- | --- | --- |
| `compare` | 一次对照请求同时看到原文、候选 | 检查候选是否保留原文的约束 |
| `blind` | 阅读器仅看到候选；另一次对照请求看到原文与阅读结果 | 检查候选能否被单独读出原有关系与约束 |

两种方式都会先做本地字面检查，包括明确的技术字面量、代码正文、URL/路径/标识符、数值、部分明确模态冲突和 `required_keywords`。本地检查没有发现冲突，只表示可以继续模型检查，不表示语义已经完整保留。

固定 `mixed` 默认生成混合语言浅树，使用 `role` / `goal` 等常见短标签，并主动将明确关系写为公共符号；简单单关系可以保持一行。校验按候选中的父节点、缩进和括号读取共享主体与条件，不要求逐句展开；盲读引文须覆盖所依赖的上层上下文。树的形态本身不证明其关系完整。

`∵` 只表达原文明示的因果，不能替代一般条件；`¬` 是否定命题，不是禁止动作。许可分支中的 `no approval` / `No审批` 表示免审批，不表示禁止审批。裸 `not/no/不/未`、前提标记“未经”及跨分支模态的作用域需要语境判断；局部无法确定时交给语义模型，不把本地未拦截当作通过。可明确确认的模态冲突、数值改变和字面量破坏仍会拦截。

编译路径使用 [`babelStructureIssues`](../../babel-go/outline.go) 检查固定形态合同。原文有至少两个可识别的独立章节标题、且并非原本紧凑或受保护格式时，候选须有至少两个带正文的 `├` / `└` / `╰` 树分支；代码、引文里的字符和空枝不计入。同时检查多个原标题是否被继续复用：删编号、加冒号、Markdown 标题、装饰树枝或内联箭头都不能代替重组，改名后仍平铺也不满足合同。

形态检查失败最多额外重组一次；仍失败则返回 `422` 与表达结构问题，保留候选供检查，但不缓存、不继续审核、不采用。只依据原文保留指定格式、必要步骤引用及原本紧凑输入的豁免；候选自行添加 `Output format:` 不能跳过检查。该合同在不开启语义校验时也执行，但不适用于独立校验已有候选的 `/api/validate`。未被引用的连续列表编号（包括 `1\.`）可移除，正文数值和实际先后关系不得丢失。

生成、对照、独立阅读和测试连接均按各自方案的请求 URL 发送 POST。当前兼容规则是：只填主机或以 `/v1` 结尾的基址时补全 `/chat/completions`；完整自定义端点原样使用，路径、末尾斜杠和查询参数保留。配置字段仍为 `base_url`。若更换已存密钥所对应地址的协议、主机或端口，必须显式提供目标服务的 Key；同源路径变化可沿用。所有这些请求均不跟随重定向，生成与校验模型响应最多 8 MiB，超限或 3xx 均不能成为校验通过。

内部生成请求将 `original` 与不可信领域参考 `domain_guidance` 放在 `user` JSON 的独立字段中；重组时另加失败草稿 `candidate`。领域资料不会进入 `system` 指令，也不会提供给后续对照或盲读阶段。

**引号本身不构成逐字保护条件。** 普通自然语言条件和活动描述允许等义压缩，例如 `「已签收未超过 7 天」` → `签收≤7天`、`参与「满 3 件 8 折」` → `参与(满3件8折)`。开启校验时，这些改写仍须经过语义对照，条件、数值及其作用域不能丢失；不因本地未拦截就判为通过。

代码、协议值和固定返回值继续按原值保护，包括大小写、空字符串和代码缩进。引号用于标示固定返回值时，须保留值本身；装饰性引号可以变化，再由模型判断是否等义。明确要求逐字保留的字符串、实际 JSON 字符串及其转义仍受完整保护；保留代码正文时可以调整 Markdown 围栏。检查依据有限的字面及上下文线索，不是完整语言解析器，含义不明的内容和复杂关系仍交给模型判断。

数值检查支持 `5 <= count` 与 `count >= 5` 这类公共比较方向的重排。数字缺失、可明确识别的比较符或单位冲突仍会拒绝。对于 `¬(count < 5)` 等命题否定，不能只按内部 `<` 判断最终约束；否定范围、列标题中的单位和跨分支条件无法在局部确定时交给模型，不能因为相同数字仍在就认定等义。`cannot`、`may not` 等有能力或可能性含义的词，也不会被一律视为明确禁止。

## 1. blind 如何隔离阅读上下文

阅读器收到固定的中立提取要求，以及最终候选文本。**不提供原文、领域表达库、编译提示词、必留词提示或额外图例。** 它提取实体、主体与动作、对象、条件、范围、模态、否定、数值及其逐字引文，并列出无法确定的歧义。

随后，对照器收到原文和这份结构化阅读结果，包括阅读器提供的引文；不再额外提供候选全文。对照器需要检查遗漏、新增和冲突，不能根据原文替阅读器补齐缺失的理解。

默认阅读器与编译器、对照器使用同一模型方案，但阅读和对照分别发起全新请求，不共享前一步的消息历史。这里的「独立」指上下文隔离；同一模型的判断仍可能相关。也可以指定另一个已保存方案作为阅读器。对照器仍使用本次编译方案。

阅读器必须返回严格 JSON。无依据的引文、明确冲突、空关系集或未决歧义会导致 `failed`；服务异常、截断响应或不合要求的 JSON 会导致 `error`。这些状态都不会通过严格门禁。

## 2. CLI 与 Web

以下命令假定已经保存好 `compiler` 和 `reader` 两个模型方案。所有选项放在输入文本之前。

```bash
# 原文与候选对照；未通过或校验异常时退出，退出码为 1
./bin/babel -profile compiler -gate -validation-mode compare -f prompt.md

# 独立盲读，阅读器使用另一个已保存方案
./bin/babel -profile compiler -gate -validation-mode blind -reader-profile reader -f prompt.md

# 本次改回同一编译方案阅读，覆盖方案里保存的 reader_profile
./bin/babel -profile compiler -gate -validation-mode blind -reader-profile= -f prompt.md

# 保存默认校验方式与阅读器；后续 CLI 仍需 -v 或 -gate 才执行校验
./bin/babel -profile compiler -validation-mode blind -reader-profile reader -save-config
```

`-v` 执行校验并报告结果，但校验 `failed` 或 `error` 时仍可输出候选；需要阻止失败候选进入后续流程时使用 `-gate`。`-gate` 本身就会开启校验，无需再加 `-v`。`-q` 隐藏统计与审计说明，不改变门禁行为。

Web 中，在「本次校验方式」选择 `compare` 或 `blind`，保持「严格校验」勾选。选择 `blind` 后，可在「本次盲读阅读器方案」选择继承方案、与编译方案相同，或另一个已保存方案。失败或异常时，后端已生成的候选仍可查看和复制，但会标为「未通过候选」或「未验收候选」，仅供检查；具体问题及盲读阶段状态同时保留。复制不会改变校验结论，未生成候选时不会展示上一轮结果。

生成或重组因长度限制等原因未完整结束时，已返回的部分文本也会保留供检查，但仍报错，不缓存、不继续审核，也不交给代理采用。审核响应即使包含可解析的通过 JSON，只要结束状态异常仍判为 `error`。候选或审核问题中提及 `API Key` 不会弹出配置窗口遮挡结果；只有当前方案实际未设置密钥且没有候选时才自动引导配置。

在「模型配置中心」保存「严格校验方式」和「盲读阅读器」，可以设置该方案的默认值。选择方式本身不会替已关闭的校验开关重新开启校验。

## 3. HTTP 编译与已有候选校验

先启动服务：

```bash
./bin/babel -serve 127.0.0.1:8080
```

服务只允许明确的环回地址，`localhost` 固定绑定到 `127.0.0.1`，不支持 `0.0.0.0` 或局域网监听。入口校验与监听地址对应的 `Host` 和端口，浏览器请求还须同源，拒绝 `Origin: null` 与跨站来源。API 和代理写请求只接受 `application/json`，入站正文最多 8 MiB；领域文件另有更小限制。页面禁止嵌入，API/代理响应强制 `nosniff` 和限制脚本执行的 CSP。原生本机客户端无须增加浏览器来源头。

### 编译并严格校验

```bash
curl http://127.0.0.1:8080/api/compile \
  -H 'Content-Type: application/json' \
  --data '{
    "text":"请求成功后，系统必须保存审计记录；请求失败时，系统禁止修改记录。",
    "profile":"compiler",
    "validation_mode":"blind",
    "reader_profile":"reader",
    "strict_gate":true
  }'
```

请求省略 `validation_mode` 或传 `""` 时，继承所选方案；方案也未设置时使用 `compare`。显式传 `compare` 可覆盖方案保存的 `blind`。`reader_profile` 省略时继承方案，显式传 `""` 时使用本次编译方案。显式指定不存在的方案名称会报错，不会自动换用其他方案。

`strict_gate:true` 时，校验通过返回 HTTP 200 和候选；校验拒绝返回 HTTP 422，校验服务或响应格式异常返回 HTTP 502。错误响应保留 `detail` 和 `validation`；若已生成候选，还包含 `compiled`、`dialect`、`cache_hit` 和 `stats`，供检查文本、计量与失败原因。**错误响应包含候选不代表候选通过或已被采用。** 若仅设置 `verify:true`、不设置严格门禁，则接口仍可返回 HTTP 200 和候选，调用方必须检查 `validation.status`。

### 只校验已有候选

`POST /api/validate` 不生成或修改候选，适合检查手写压缩文本和运行评测。它始终执行所选校验，不需要 `verify` 或 `strict_gate`。

```bash
curl http://127.0.0.1:8080/api/validate \
  -H 'Content-Type: application/json' \
  --data '{
    "text":"请求成功后，系统必须保存审计记录；请求失败时，系统禁止修改记录。",
    "candidate":"请求成功后：系统须保存审计记录；请求失败：系统禁止修改记录。",
    "profile":"compiler",
    "validation_mode":"blind",
    "reader_profile":"reader",
    "required_keywords":["审计记录"]
  }'
```

响应主体为 `{"validation": {...}}`。此接口把「检查完成但未通过」视为正常评测结果：

| HTTP 状态 | `validation.status` | 含义 |
| --- | --- | --- |
| 200 | `passed` | 本次检查通过 |
| 200 | `failed` | 检测到缺失、冲突或歧义；候选未通过 |
| 502 | `error` | 阅读/对照服务异常，或模型响应未满足格式与完整性要求 |
| 400 | 无 `validation`，返回 `detail` | 参数错误，例如空文本、未知校验方式或不存在的方案 |

**HTTP 200 本身不是通过标志。** 应读取 `validation.status`，不要搜索响应文字里是否出现 `PASS`。对照模式的方法为 `llm_compare`；如果先被本地检查拦截，则为 `local_checks`。盲读模式的方法始终为 `blind_read`。

盲读结果还包含 `stages`：`local_checks`、`reader`、`comparator`。前两步正常完成时为 `completed`；只有对照通过才得到整体 `passed`。未执行的后续阶段为 `not_run`。阅读器阶段的 `reading` 可用于查看模型实际读出了什么；`model` 是配置中的模型名称。

## 4. 代理使用

OpenAI `/v1/chat/completions` 与 Anthropic `/v1/messages` 代理均支持以下请求头：

```text
X-Babel-Profile: compiler
X-Babel-Validation-Mode: blind
X-Babel-Reader-Profile: reader
```

省略请求头时继承所选方案；方案未设置校验方式时使用 `compare`。`X-Babel-Reader-Profile` 需要指向已保存方案；显式发送空值可以清除继承的阅读器，改用本次编译方案。

代理只尝试压缩 `user` 消息的字符串内容或显式 `text` 块，并对每个实际编译的块执行严格校验。OpenAI 的 `system` / `developer`、Anthropic 顶层 `system`、assistant 历史、工具定义与描述、工具调用和工具结果均保留原字段值，不交给编译模型重写。生成候选仍放回原 `user` 文本位置，不升级消息角色。

只有所选校验通过，且候选在所选计数方式下 token 更少，才采用候选。Babel 的生成、校验或计数失败，或候选未变短时保留原文，继续向最终上游转发请求。最终上游的普通错误响应继续返回；3xx 重定向转为 HTTP 502，不透传 `Location`，避免客户端继续转发 prompt 和凭据。配置参数本身无效时返回 HTTP 400。

流式请求保留客户端提供的 `stream_options`，不为了统计而自动添加 `include_usage`；实际用量只在上游返回时记录。回退同样保留图像等非文本消息块、客户端协议选项及流式响应，不重发最终请求。非流式响应为 usage 统计最多保留 1 MiB 副本，超过后放弃统计，不截断实际转发的正文；SSE 使用有界的首部或尾部采样。生成与校验模型的 8 MiB 响应上限不套用到最终上游响应。

这些请求头不改变最终消费模型。方案中的请求 URL、API Key 和模型用于编译及对照，阅读器可另用自己的方案；请求体中的 `model` 和客户端认证信息属于最终上游。OpenAI 代理必须收到调用方的 `Authorization`；Anthropic 必须收到调用方的 `x-api-key` 或 `Authorization`。缺失时返回 HTTP 401，不借用编译密钥。代理的 `upstream_url` / `X-Upstream-BaseURL` 表示最终服务基址，按相应协议构造转发路径。OpenAI 代理未指定基址时原样使用编译请求 URL；Anthropic 代理须显式指定基址。所有最终转发也拒绝重定向。具体接入见 [README](../../README.md#http-api-与代理)。

## 5. 调用次数、缓存与成本

下表以一段文本、各阶段均正常执行完毕为前提，计数的是 Babel 发起的模型请求，不包括代理最终转发的上游请求：

| 操作 | 未命中生成缓存 | 命中生成缓存 |
| --- | --- | --- |
| 只编译，不开启校验 | 1 次生成 | 0 次 |
| 编译并 `compare` | 1 次生成 + 1 次对照，共 2 次 | 1 次对照 |
| 编译并 `blind` | 1 次生成 + 1 次阅读 + 1 次对照，共 3 次 | 1 次阅读 + 1 次对照，共 2 次 |
| `/api/validate`，`compare` | 1 次对照 | 不查询生成缓存，仍为 1 次 |
| `/api/validate`，`blind` | 1 次阅读 + 1 次对照，共 2 次 | 不查询生成缓存，仍为 2 次 |

生成候选违反形态合同时，表中的生成部分最多增加 1 次重组请求；仍失败就结束，不再进行阅读或对照。不合格的缓存候选不会复用，按未命中处理。网络异常和语义拒绝不触发这轮结构重写。

本地检查提前拒绝时不调用验证模型；盲读阶段失败时不再调用对照器。并发的相同生成请求可以共享一次生成，但**每个请求都独立执行自己的校验，验证结果不缓存**。切换校验方式不会让旧审计结论成为本次通过依据。

生成缓存只保存正常完成生成且形态合格的候选，读取时仍检查形态。形态合格的候选之后被语义拒绝，也可能留在缓存中，但每次请求仍按本次设置重新计数和校验。若要重新生成，用 CLI `-no-cache`、编译 API `no_cache:true` 或 Web 的强制重编译；它们跳过本次生成缓存读写和并发生成共享。

HTTP 请求取消或连接关闭时，本次阅读、对照和 `no_cache:true` 的生成请求会随之取消，不再发起后续验证。已开始的共享生成可能继续完成并写入候选缓存，以供仍在等待的请求使用；取消者会退出等待，也不会继续验证。发送取消不能保证供应商立即停止计算或撤销已经产生的费用。

代理的一次请求可能包含多个可压缩 `user` 文本块，每个块分别产生上述调用；高权限消息、工具定义和工具结果不会产生编译调用。短文本块或熔断期间直接保留原文，跳过编译。已经发生的生成、阅读或对照费用，不会因为最终采用原文而消失。

`blind` 比 `compare` 多一次阅读请求，并让后续对照读取结构化抽取结果；延迟和费用会增加，具体取决于文本长度、阅读结果长度和各模型定价。是否划算应同时计算编译/验证开销与最终消费请求的节省，不能仅凭压缩比例判断。文本计数的范围见 [目标 tokenizer 计数](token-counting.md)。

## 6. 如何理解「通过」

`passed` 是所选模型、候选和本次校验策略下的检查结果，不是语义等价的形式证明。模型可能遗漏关系或共同误判；一次或几个模型通过，也不能据此承诺「任意强模型无需图例都能正确理解」。

原文回退不等于恶意提示词清洗：原文若带有恶意指令，回退仍会转发这段原文。模型生成、阅读和对照服务都需要被信任；数据字段隔离、角色保留和严格结果解析不能保证模型不会被文本误导或共同给出错误结论。本机原生进程、运行账户及其配置文件仍属于信任边界，这个本地工具没有不同本机用户之间的授权隔离。

盲读提供的是可检查的阅读证据。若要评估实际可靠性，应保存原文、候选、模型配置、策略版本、阅读结果和问题列表，并在代表性文本及真实下游任务上比较表现。已有离线回归测试验证请求隔离和失败处理，不等同于真实模型的语义准确率评测。
