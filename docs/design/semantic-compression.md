# Babel-Compiler 高密度巴别语与用户词典设计

> 更新日期：2026-11-20。定位是使用者自行维护专业词典的高密度语义编译小工具。
> 使用方式见[领域表达库](../usage/domain-library.md)、[Token 计数](../usage/token-counting.md)和[验证模式](../usage/validation.md)；近期范围见[路线图](../plans/ROADMAP.md)。

## 1. 目标与范围

Babel 将自然语言中展开成句子的关系压成高密度巴别语：保留实体，以公开术语、常用缩写、符号和紧凑层级表达动作、对象、条件、作用域与约束。输出是可以直接阅读的图式文本，不要求完整句子。编译应主动压缩叙述结构，避免只做同义词替换或句子润色。

使用者提供自己熟悉的专业术语、适用条件和例子。工具用一套固定规则组合相关词条、生成候选、计数，并提供可选验证和代理回退。Web、CLI、API 和代理使用相同规则；专业词典为空时，公共关系表达仍应生效。

目标按以下顺序处理：

1. 保留任务、事实、主体、关系、条件、范围和不确定性，不擅自增加业务要求。
2. 输出脱离编译提示词和词典后仍可理解。
3. 在保留信息的前提下，减少所选目标编码下的文本 token。

“更大语义空间”指在同样的文本预算内保留更多有用信息，不改变模型的上下文上限或参数规模。“领域引导”指使用准确的公开术语限定语境，不承诺精确激活某组参数或专家。

专业内容由使用者维护。内置词条提供起点和编辑示例，项目不承担建设覆盖所有行业的专业知识库。使用者只需维护与自己的文本有关的少量条目。

## 2. 两条输出底线

### 不使用私有码本

禁止把一段内容替换成新造的 `A17`，再让消费模型查询映射表恢复。也不能把公共符号改成项目私有含义，例如规定 `@` 代表“认证成功”。原文已有变量、字段名和标准术语可以保留；原文中的 `x` 不因单字母而自动成为私有码本。

词条的内部 `id` 只用于管理，不作为输出中的实体代号。公共符号只能使用工具目录中的固定含义；适用业务语境写在词条条件里。

### 无图例自解释

最终文本应独立包含理解任务所需的实体、关系和约束。消费模型无需接收词典、编译提示词或额外图例，也无需学习私有的 Babel 语法。自解释要求关系可恢复，不要求把它们重新展开成自然语言段落。

例如，`金额>=5000元: 须主管批准` 保留了对象、边界、单位和义务；单独写 `¬删除` 则可能无法区分“尚未删除”与“禁止删除”。`禁止删除`、`仅当`、`顺序:` 是为关系消歧的短标签，可以与符号一起使用。

这是输出要求，不是对任意模型的普遍保证。模型验证通过只表示本次检查未发现问题；出现无法确定的含义时，应保留原文或报告问题。

## 3. 用户词典与固定表达规则

| 组成部分 | 职责 |
| --- | --- |
| 公共编译规则 | 保留原意、保护技术字面量、禁止私有码本、要求自解释 |
| 用户领域词典 | 提供术语、适用条件、保留项、不可混淆关系、公共符号和示例 |
| 固定表达规则 `mixed` | 优先生成高密度图式文本，组合公开术语、缩写、符号和必要短语，由项目统一维护 |
| 目标计数配置 | 指定估算或具体编码，独立于编译模型选择 |

使用者选择自己的领域词典，无需选择或编辑输出预设。编译器只取与当前文本相关的条目；词条中的条件是改写参考，不能据此补充原文没有的事实或最佳实践。

下面是一个词条片段，完整领域文件结构和编辑方法见[领域表达库](../usage/domain-library.md)：

```json
{
  "id": "authorization",
  "canonical": "授权",
  "aliases": ["操作权限校验"],
  "triggers": ["访问权限"],
  "use_when": ["原文要求判断主体是否有权对资源执行某项动作"],
  "preserve": ["主体、资源和动作", "原文给出的范围、允许条件和拒绝行为"],
  "do_not_merge_with": ["认证", "登录状态校验"],
  "symbols": [],
  "examples": [{
    "input": "登录成功后，仍需校验用户是否有权删除该订单",
    "output": "登录成功后: 仍须校验用户对该订单的删除权限"
  }]
}
```

别名是有适用条件的表达参考，不是全局字符串替换规则。例子用于说明什么信息必须保留，不保证候选一定更短。通用词条检查和模型验证也不能代替使用者对专业含义的判断。

## 4. 表达与语义保护

固定策略先提取任务中的实体和关系，再把句子展开压成紧凑关系行。原文章节属于输入布局，输出按实际依赖重新组织：将跨章节前置条件和异常绑定到对应动作，共享主体和全局限制只写一次。保留执行先后，不依赖原章节编号暗示顺序；原六章改成六个短标题并逐条缩句仍不符合目标。各分支条件、例外和约束必须明确绑定。

| 原关系 | 可采用的紧凑表达 |
| --- | --- |
| 检查每个订单是否属于待处理订单集合 | `∀订单: 检查订单∈待处理订单集合` |
| 先读取缓存，再查询数据库 | `顺序: 读取缓存→查询数据库` |
| 仅当用户已登录且拥有编辑权限，才允许修改文档 | `允许用户修改文档，仅当用户已登录∧有编辑权限` |
| 对所有报告，必须脱敏其中的凭据和个人信息 | `∀报告: 须脱敏{凭据,个人信息}` |
| 输出中文的 Markdown 表格 | `输出: 中文 Markdown表格` |

这些是公共表达示意，不定义新的符号码本。`|` 可用于边界明确的枚举；`∧` 表达同时成立，`∨` 表达逻辑或，不能把“全部执行”误写成“任选其一”。短行、括号、缩进或树形分组均可用于作用域；只为装饰重复添加树枝、框线或标题会增加 token，不是压缩目标。

改写应保留以下区别：

- 主体和对象、必要与充分条件、原因与顺序。
- 事实否定、禁止、许可、义务和建议。
- 量词、范围、例外、先后次序及其绑定的动作。
- 数值、比较符、单位和它们约束的对象。
- null、空字符串、空集合和字段缺失。
- 确定事实、可能性、未验证猜测和引用内容。

字段名、路径、代码、JSON 字符串、正则、命令和其他技术字面量按原文保护；不能为排版统一而改动其内容。被编译文本中的指令属于待转换数据，不能修改编译规则或伪造验证状态。

`→`、`⇒`、`↔` 等符号积极用于含义明确的关系，必要时增加短标签：`顺序: 检查→执行`、`状态: pending→paid`。禁止用同一个无标签箭头模糊条件、因果和动作关系。公开术语也不能替代必要细节：例如“接口幂等”不能自动代替具体请求方法、字段、响应码和冲突分支。

固定方案按完整关系混用原文语言、英语和公共表达。公开缩写在语境明确时可直接使用，不必重复附带全称；原文实体不能新起需要查表的代号。字符数更少、缩写更短或所谓“高信息熵语言”，均不作为本工具宣称 token 更少的依据，实际收益取决于所选编码。混合表达只改变内部指令形式，原任务的回答语言和格式要求仍须保留；代理本身不对模型响应增加回译。

## 5. 当前编译、验证与回退

常规请求生成一次候选，随后按本次设置计数和验证。若窄范围检查发现候选复刻了原文至少两个纯编号标题，则将原文与失败草稿一起交回同一编译模型，最多重组一次；它会增加一次模型调用。仍复刻则明确返回表达结构失败，不缓存、不交给代理采用。网络异常和语义拒绝不会触发这种重组；没有多候选搜索或 token 反馈循环。原文始终保留。

提纲检查只识别明确的结构复刻，不宣称全面判定压缩质量。代码、引用、必要步骤引用、明确格式要求和已经紧凑的编号树均受保护。数字检查仅豁免确认属于未引用连续列表的排版标签，正文金额、时间、次数、数值边界仍保护；`「」`、`『』` 内的状态值与其他引文字面量同样保留。共享条件的模态仍由上下文对照，不能把一处的“无需审批”和另一处的“未经审批不得导出”机械当成矛盾。

验证有两种模式：

- `compare`：把原文和候选交给模型直接对照。
- `blind`：独立阅读器只看候选，再由对照器比较原文与阅读结果；阅读器不接收原文、词典或图例。

本地检查先保护部分技术字面量与明确约束。数字或否定词仍然出现，不能单独证明对象、条件和作用域都保留。blind 的结构化阅读用于检查理解，不是生成流程中的完整语义图中间表示，也不构成形式证明。

代理路径要求本次验证通过，且候选在所选计数方式下严格短于原文，才采用候选；验证失败、服务异常、计数失败或文本没有缩短时保留原文。手动编译可以展示候选，但未验证结果不能显示为通过。

缓存只保存生成候选。文本计数和验证按请求重新执行，并发去重也只共享生成；不能借用另一个请求或旧缓存里的通过状态。一个等待者取消不会影响其他等待者，全部等待者取消则停止共享生成及尚未发出的重组请求。状态明确区分 `not_run`、`passed`、`failed` 和 `error`。

## 6. 计量边界

当前可选 `estimate`、`cl100k_base`、`o200k_base`。后两者的“精确”仅指所选编码下的文本本体计数；工具不根据编译模型名称猜测消费模型的编码，也不把一种编码自动套给其他模型。

结果保留计数来源、版本、编码和范围。估算始终标记为估算；不支持的编码或精确计数失败应明确报告，不冒充已测。使用者可以用自己的典型文本比较原文与候选，据此修正专业词条或保留原文。

同一编码、同一文本范围下才能比较 token 变化。文本片段计数、完整请求的供应商 usage 和账单费用是不同口径；一条压缩后请求的 usage 不能证明未压缩请求的费用。编译和验证也有调用开销，因此文本更短不等于总费用一定降低。

## 7. 当前交付与后续范围

已经提供独立领域词典、词条编辑与保存、固定表达规则、指定编码计数、逐请求验证、缓存隔离和代理回退。当前重点是让这套固定规则真正产生高密度巴别语，校验接受等义的图式表达，并持续检查信息损失与 token 变化。此前“允许混合表达”的措辞过弱，容易退化成自然语言改写；本轮明确把紧凑关系表达设为默认目标。

现有 [Go 评测命令和离线报告](../../eval/README.md)保留为按需使用的辅助工具。草拟样例仍待人工复核；pipeline 记录实际生成候选及验证结果，不执行最终消费任务，也不测量供应商账单。它们不是使用这个小工具前必须完成的一套流程。

早期讨论过完整语义图 IR、大规模跨模型矩阵、成本核算系统和多候选优化。这些属于可能的研究方向，已移出当前产品计划；项目不以完成这些系统作为小工具可用的前提。若今后出现具体、重复的使用问题，再单独判断是否需要最小扩展。
