# Babel-Compiler 语义图表达与领域词典设计

> 状态：公共规则、独立领域库、输出预设、逐请求验证与缓存隔离已实现；现已接入 `cl100k_base` / `o200k_base` 本地计数、按所选计数回退及可选独立盲读。真实模型的跨模型语义效果、完整关系表示和下游任务行为评测仍待验证。
> 更新日期：2026-11-19。初次审查基线：`839055a5f2a4b3dda3c08190fe23d2769b75cc17`。使用方式见[领域表达库](../usage/domain-library.md)、[Token 计数](../usage/token-counting.md)和[验证模式](../usage/validation.md)。

## 1. 项目定位与目标

Babel-Compiler 面向需要反复交给大模型读取的提示词、操作规范和技术说明，将其中的实体、关系、条件与作用域改写为紧凑、可直接理解的语义图表达。
自然语言经常把关系网络展开为一串便于人类阅读的句子，重复主语、连接词和背景。项目希望减少这部分展开成本，显式保存“谁对谁做什么、因为什么、在什么条件下”的结构。
常见文本大模型仍然读取 token 序列；这里的“直接读图”指读取语义图的紧凑文本序列化，不是新增原生图输入，也不是绕过 tokenizer。
语义图可以由带关系名称的短句、规则列表和公开符号共同表达；无需把所有关系强行改成数学式。
`A→B`、`X∈Y`、`P∧¬Q` 可用于讨论结构，实际输出应保留原文实体名称及关系类型，不能留下需要查表的节点代号。
核心工作是保留关系并减少表达开销；任务指令、证据强度、先后顺序、例外和否定范围都属于图的一部分，不能只留下关键词。

目标按以下顺序执行：

1. 保留原文的任务、事实、适用范围、约束和不确定性，不擅自补充业务要求。
2. 输出无需外部图例或私有词表即可理解，并在明确的目标模型集合上验证。
3. 在前两项通过后，减少目标模型实际读取的 token。
4. 用原文已有的准确领域概念减少歧义，检验下游任务是否更稳定。

“更大语义空间”在本项目中指：在相同上下文预算内承载更多经验证保留的信息，不改变模型的上下文上限或参数规模。
“领域引导”指通过术语、对象和关系限定任务语境；不宣称能够精确选择、激活某组模型参数或专家，也不将模型内部机制作为验收指标。
压缩率是测量结果。不存在适用于所有语言、文档、tokenizer 和任务的固定最佳比例。

## 2. 两条不可退让的输出要求

### 2.1 不使用私有码本

禁止新增需要查表才能解释的实体代号，例如把某段文字替换成 `A17`，再依靠另外的映射表恢复。
也禁止将公共符号赋予项目私有含义后，假定其他模型自然知道：例如不能规定 `@` 同时代表任职、身份认证成功和运行状态。
原文已有的变量、字段名和标准术语应保留；`x` 是原文变量时，不因单字母而被误判为私有码本。

### 2.2 无图例自解释

最终发送给消费模型的文本，必须独立包含理解任务所需的实体、关系、范围和条件。
消费模型不接收领域词典、编译提示词或还原对照表，也不应依赖“先学习 Babel 语法”。
必要的短语或上下文标签可以保留，例如“数据流”“禁止”“仅当”，其 token 计入最终结果。
“任意强模型可读”是产品方向；可交付的证据是指定模型、版本、语言与任务集上的验证结果，不能推广成普遍保证。

| 表达 | 判断 | 原因 |
| --- | --- | --- |
| `金额 >= 5000 元时，须主管批准` | 可作为候选 | 比较对象、边界、单位和义务完整 |
| `A17 -> B3`，含义在另一份词表中 | 禁止 | 新造指代编码依赖外部映射 |
| `禁止删除审计日志` | 可作为候选 | 禁止义与作用对象明确 |
| `¬删除` | 不宜默认使用 | 可能表示未删除、不要删除或删除条件为假 |
| 保留原文的 `ETag`、`If-Match` | 可作为候选 | 原有技术实体不被自造简称替代 |

## 4. 四个可组合的配置部分

| 部分 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 公共编译规则 | 保留语义、禁止私有码本、保护技术字面量、要求可独立阅读 | 不规定必须使用多少符号 |
| 领域表达库 | 提供公开术语、等价表达、允许使用的符号及边界 | 不注入原文没有的事实或最佳实践 |
| 输出预设 | 选择简洁自然语言、规则列表或适量符号，以及语言和排版 | 不独占领域规则，不绕过公共约束 |
| 目标 tokenizer 配置 | 选择计数方法、模型/编码版本、不可用时的处理方式 | 不用编译模型的 tokenizer 代替消费模型 |

“领域表达库”是方言词典的目标形态。可以同时选择“应用安全”和“API 契约”，再选择“简洁中文”输出预设。
词典帮助编译器选用公开表达；它的存在不意味着消费者需要解码词典。
只将与当前文本相关的词条提供给编译器，避免每次注入整个领域库，增加编译成本或诱导模型扩展任务。
初期使用本地文件和少量明确条目即可；不需要先建设向量检索、完整形式语言或新的数据库。

### 4.1 从自然语言到带类型关系

以下为完整设计示例，未实测 token 或跨模型行为；若实际不更短，则保留原文。

```text
原文：支付网关向支付服务发送回调。支付服务仅在回调签名有效且订单未取消时，才可处理该回调。回调签名无效时，禁止修改订单，并返回 401。处理回调成功后，支付服务记录审计日志。

关系表达：
发送回调: 支付网关 → 支付服务。
处理回调的主体: 支付服务。
允许处理回调的必要条件: 回调签名有效 ∧ 订单未取消。
回调签名无效时: 禁止修改订单，并返回 401。
顺序: 支付服务处理回调成功 → 支付服务记录审计日志。
```

“发送回调”和“顺序”限定箭头含义；“必要条件”保留“仅在……才可”的方向，不能改成条件满足就必须执行。
事实否定“订单未取消”与规范禁止“禁止修改订单”分别保留。条件分支不能被写成已经发生的事实，也不能自动补出失败原因。
类似地，因果边应明确写“原因/导致”，成员关系才使用 `∈`；时间窗口、例外和适用范围必须绑定到相应动作或关系。

### 4.2 原子关系的内部表示

可以使用轻量结构记录编译前后的关系，辅助对照和验证；下列 schema 为拟议内部格式，不是要求消费模型解析的新语言。
单条原子关系表达一项动作或约束，并携带其条件与范围；拆行不能把条件从原动作上剥离。

```yaml
schema_version: 1
relations:
  - subject: 支付网关
    relation: 发送
    object: 回调
    recipient: 支付服务
  - subject: 支付服务
    relation: 处理
    object: 回调
    modality: 允许
    necessary_conditions:
      all: [回调签名有效, 订单未取消]
  - when: 回调签名无效
    constraints:
      - {relation: 修改, object: 订单, modality: 禁止}
      - {relation: 返回, object: 401}
  - subject: 支付服务
    relation: 记录
    object: 审计日志
    after: 支付服务处理回调成功
```

内部还可记录来源位置、证据状态和未解决歧义；这些元数据不代替最终文本中的真实实体与关系。
字段未在原文确定时保持未知，不根据常见业务流程填空。内部表示本身也由检查或人工样例校验，不能把一次模型抽取视为正确答案。
初期可以先用这类结构完善验收样例，运行时仍沿用现有模型编译流程；不必先实现图数据库或完整逻辑推理器。

## 5. 领域词条结构与示例

### 5.1 建议的数据结构

以下 YAML 保留原始设计示例；运行时采用 JSON，字段以[使用指南](../usage/domain-library.md)为准。示例表达尚未进行目标 tokenizer 或跨模型实测。

```yaml
schema_version: 1
id: application-security.authorization
version: 1
domain: application-security
canonical: 授权
aliases:
  - 操作权限校验
  - 访问权限判定
use_when:
  - 原文要求判断主体是否有权对资源执行某项动作
required_slots:
  - 主体
  - 资源
  - 动作
preserve_when_present:
  - 租户范围
  - 允许条件
  - 拒绝行为
do_not_merge_with:
  - 认证
  - 登录状态校验
allowed_symbols: []
examples:
  - input: 登录成功后，仍需校验用户是否有权删除该订单
    output: 登录成功后，仍须校验用户对该订单的删除权限
counterexamples:
  - 登录成功即可删除订单
```

`id` 用于内部管理，不替换输出中的语义内容。`aliases` 是有条件的候选关系，不是全局字符串替换规则。
词条至少记录适用范围、必须保留的信息及反例；公开标准术语还应附出处，便于审查其真实含义。
若添加符号条目，需记录公开含义、允许的语境、禁止合并的关系，以及明确命名实体的正反例。
多个领域词条冲突时保留原文，不由加载顺序决定最终语义。

### 5.2 应用安全

原文：

```text
仅可对测试环境执行只读检查；不得写入数据；未验证的猜测应单独列入待确认，不得列入已确认漏洞。
```

候选：

```text
范围: 仅测试环境。检查须只读，禁止写入数据。
未验证猜测: 单列待确认，禁止列入已确认漏洞。
```

保留“仅”“禁止”“未验证”和两类清单的区别。不得只留下 `¬写入`、把猜测升级为漏洞，或因安全领域词典而新增测试动作。

### 5.3 API 契约

原文：

```text
POST /orders 必须携带 Idempotency-Key。同一 Idempotency-Key 且请求体相同，返回首次结果；同一 Idempotency-Key 但请求体不同，返回 409，不创建新订单。
```

候选：

```text
POST /orders: 必须携带 Idempotency-Key。
同一 Idempotency-Key: 请求体相同则返回首次结果；请求体不同则返回 409，禁止创建新订单。
```

这里保留方法、路径、字段拼写、响应码和分支条件。词典可以识别“幂等”概念，但不能用“接口幂等”四字替代所有业务细节。

### 5.4 并发与版本条件

原文：

```text
原子地检查记录 version 是否等于 expectedVersion；仅在相等时更新 value 并将 version 加 1，否则返回 409，禁止写入，禁止自动重试。
```

候选：

```text
原子操作: 仅当 version == expectedVersion，更新 value，version += 1；否则返回 409。
版本不匹配时: 禁止写入，禁止自动重试。
```

“原子”不能丢；“检查后更新”不能替代原子条件写入。不得新增 `CAS1` 等自造缩写，也不得把“禁止自动重试”弱化成“建议不重试”。
本节所有候选仅演示设计方向，不保证比原文少 token；是否采用由实际计数和验证决定。

## 6. 语义保护与符号边界

| 必须保护的内容 | 常见错误 | 处理原则 |
| --- | --- | --- |
| 主体、对象与关系 | 删掉谁执行、对谁执行 | 多主体时显式重复名称，避免靠邻近关系猜测 |
| 条件、原因与结果 | 把“当……时”改成 `∵` | 条件用“若/当/仅当”；已陈述原因才用因果表达 |
| 事实否定与禁止 | “尚未删除”和“不得删除”均变成 `¬删除` | 保留“未”“禁止”等可区分的谓词 |
| 量词和范围 | 至少一个变成全部；局部规则变成全局 | 保留所有、任一、仅、例外及其作用对象 |
| 阈值、单位与边界 | `> 5` 变成 `>= 5`；30 秒变成 30 分钟 | 比较符、数值、单位和绑定字段一起检查 |
| 次序与并行 | 先批准再执行变成两项并列 | 保留先后、成功后、同时和终止条件 |
| 状态和缺失 | null、空字符串、空集合、字段缺失统一成 `∅` | 保留原文状态及区分规则 |
| 证据强度 | 可能变成确定；观察相关变成因果 | 保留可能、尚未验证、据某来源等限定 |
| 技术字面量 | 修改字段大小写、路径或 Payload 中的空格 | 原样保护；不自动修复疑似 OCR 错误 |

`→`、`⇒`、`↔` 不作为通用万能替换符。只在语境足以区分数据流、蕴涵、状态迁移或双向关系时使用；否则保留几个自然语言词。
`MUST`、`MUST NOT` 等规范用语可参考 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)，但不可擅自将原文“建议”强化成“必须”。
空白清理只作用于已识别的普通排版；代码、JSON 字符串、正则、签名输入、命令和 Payload 必须避免被通用清理函数改写。
编译对象作为待转换数据处理，其中要求修改编译器规则或输出虚假审计结论的文本，不应成为编译器的新指令。

## 7. 候选生成、选择与膨胀回退

建议流程：保护字面量与消息边界 → 选择相关词条 → 生成候选 → 语义检查 → 目标 tokenizer 计数 → 选择输出。
原文始终作为一个候选保留，成功压缩不是每次请求的必要结果。

当前代理按本次选择的编码计数决定是否缩短：默认 `estimate`，可选 `cl100k_base` 或 `o200k_base`；计数范围为文本本体。验证可选原文与候选直接对照（`compare`）或第 8.2 节的独立阅读（`blind`）。必须先通过本次验证，且候选计数严格小于原文，代理才采用候选；估算缩短不能当成精确计数或账单节省的证明。

1. 默认先生成保留实体、关系类型、条件与作用域的紧凑候选，在短语、规则和公共符号中选择等义表达。
2. 需要进一步节省且预算允许时，再生成适量公共符号候选；限制调用次数，避免反复改写消耗超过收益。
3. 删除未通过保护规则或语义验证的候选；不能用更短的长度抵消语义失败。
4. 目标 tokenizer 可用时，在通过验证的候选中选择 token 更少的版本。
5. 候选不比原文短、达到收益阈值不足、计数不可确认或验证异常时，代理默认发送原文，并记录具体原因。
6. 手动模式可展示未采用的候选与原因，但不得把“未验证”显示为通过。

字段、工具参数 schema、消息 role 和结构化协议保持原有边界；只改写允许的文本部分。
针对自然语言中的来源引用、引用范围和对话指代，验证上下文是否仍在实际发送的消息中；无法独立保留时不压缩该片段。
不预设 ASCII 一定更省，也不因 Unicode 看起来只有一个字符就认定其 token 更少。

## 8. 验证：保留信息与保持行为都要检查

### 8.1 可确定检查

优先检查技术字面量、枚举、单位、字段和边界条件；对明确的比较表达可以用结构化规则核对。
数字或否定符号“出现过”只能作为弱检查，不能证明它仍绑定同一对象或作用域。
用人工标注样例验证检查器，包括删除一条禁止规则、交换阈值、翻转比较符、交换执行顺序等变体。

### 8.2 独立阅读与对照

当前已实现 `blind` 模式：阅读器提取实体及带条件、范围、模态、否定、数量和逐字证据的关系；对照器只收到原文与阅读结果。严格 JSON、引用依据及阶段状态校验已接入。默认两个阶段沿用编译方案，但使用独立请求；也可以指定另一个已保存的阅读器方案。模型字段记录配置名称，不表示供应商实际部署版本已经独立核验。下列流程的真实模型准确率仍需评测。

1. 编译器读取原文并生成候选。
2. 阅读器在独立请求中只看到最终候选，以及固定的中立提取要求；不提供原文、词典、编译提示词或缺失提示。
3. 阅读器提取主体、动作、条件、例外、禁止事项、范围、数值和不确定性，并标记无法确定的关系。
4. 比较器再将该结果与原文约束或人工标注清单对照，识别缺失、新增、冲突与歧义。

步骤 2 的隔离是无图例自解释的主要验证条件；同时展示原文和候选的评审无法替代它。
使用不同模型可以降低同源偏差，但也不能将一次通过视为形式证明；记录每个参与模型、版本、参数及验证规则版本。
阅读器若必须借助图例才能恢复含义，该候选即不符合产品目标，不通过“补发图例”修补。

### 8.3 下游任务行为

原文和候选分别进入隔离的同类任务，比较输出格式、关键决策和执行约束，不仅比较自然语言复述相似度。
API 用例覆盖方法、响应码、字段缺失、边界值；并发用例覆盖版本相等/不等、重试和副作用；安全规范覆盖范围、权限及证据分类。
固定输入、模型配置和判分标准；有随机性时采用重复样本，报告样本数与失败例，不只挑选成功案例。
至少分别记录：原文成功率、候选成功率、关键约束违反数、歧义数、token 变化及回退率。
在原文也失败的用例上，不能单凭候选失败认定压缩引入了回归；仍需保留该用例作为产品局限。

## 9. 真实 token 计量与成本

token 计量必须面向消费模型。可使用官方 tokenizer 或官方计数接口；例如 [tiktoken](https://github.com/openai/tiktoken) 提供编码及模型映射，不能据此假定其他模型共用该编码。
每次结果附上 `measurement_kind`、模型/编码名称、版本、计数范围和来源；估算结果明确标记 `estimated`，未知结果标记 `unknown`。
文本本体 token、完整请求 token、供应商 usage 和账单费用分别呈现，不混成一个“实测压缩率”。

同一 tokenizer、同一计数范围下：`节省率 = 1 - 候选 token / 原文 token`；原文为空时不计算比例。
完整请求还应包含实际发送的系统消息、消息封装、工具 schema 及必要上下文；只统计改写片段不能代表整次请求的节省。
压缩后请求的实际 usage，只能证明该次请求的用量；未压缩请求若没有同口径计数或对照调用，其用量仍是估计。

端到端成本至少包含编译输入/输出、验证输入/输出、失败重试、下游输入/输出及缓存价格影响。
建议显示一次性成本和复用后的累计净收益，避免“下游少了 token”被误认为“总成本一定下降”。
当前验证不缓存，每次请求都会重新验证，不能把验证费全部当成一次性成本摊薄。只有“每次下游实际节省费用 − 本次验证及其他新增费用”为正时，才可按 `一次性编译费用 / 每次净节省费用` 向上取整估算回本复用次数；价格、失败率与缓存条件改变时重新计算。
延迟单独记录编译、验证和消费阶段的耗时；对仅使用一次的短文本，允许直接跳过编译。

## 10. 编译缓存与验证隔离

编译缓存仅代表某份配置下生成的候选。建议键至少覆盖原文内容哈希、编译供应商/端点身份、模型版本、公共规则、领域条目版本和输出预设。
若目标 tokenizer 或长度预算影响候选生成，也必须进入编译键；不把 API Key 明文作为缓存键内容。
原文哈希应保留技术字面量的原始内容，不能先对所有空白进行无条件归一化。

当前只缓存生成候选，验证与文本计数都按请求重新执行。若后续增加验证缓存，键必须覆盖原文与候选内容哈希、验证策略版本、阅读器/比较器版本和本次所需约束。
若增加 token 计数缓存，应另按候选内容和目标编码版本建立；更换消费模型后不能复用旧编码下的计数结论。
审计状态使用结构化枚举，例如 `passed`、`failed`、`error`、`not_run`；禁止根据字符串中出现 `PASS` 就放行。
无法解析的响应、调用失败和超时都是未通过验证；严格路径回退原文或返回明确失败，不沿用旧的成功文本。
并发去重只共享候选生成；每个请求分别满足自己的验证策略，严格请求不得借用宽松请求的验证状态。
旧缓存仅作为未验证候选读取，旧审计字符串不作为通过证据；当前实现不持久化验证通过记录。

## 11. 分阶段实施与验收

功能实现与效果验收分开记录。以下“已实现”指代码、离线回归及 mock 集成通过，不等于真实模型准确率已达标。

| 阶段 | 状态与交付内容 | 验收证据或剩余条件 |
| --- | --- | --- |
| P0：修正语义与状态 | 已实现：保留技术文本、结构化审计、逐请求验证、错误及缓存隔离 | `compiler_test.go` / `proxy_test.go` 覆盖字面检查、错误响应、缓存与并发请求；不能证明任意语义等价 |
| P1：拆分词典与预设 | 已实现：公共规则、独立领域条目、预设与来源覆盖管理 | `domains_test.go` / `domain_integration_test.go` 覆盖安全、API、并发领域的组合及保存、覆盖、迁移 |
| P2：计量与候选回退 | 已实现：两种指定编码、本地计数、完整来源与按请求回退 | 29 条独立官方参考文本 × 2 编码一致；代理有“估算缩短但实际编码膨胀”的回退回归 |
| P3：跨模型语义验收 | 部分实现：独立阅读、结构化关系提取、分阶段状态及已有候选验证 API | 隔离请求与失败关闭有 mock 回归；仍缺经人工复核的样本、真实模型矩阵、任务行为、费用与延迟对照 |

首轮建议冻结至少 60 个中文、英文及混合技术文本样例，覆盖上述三类领域和短文本、长规范、嵌套条件、重复数字、例外及否定范围。
从中保留至少 20 个不参与词条调试的样例；不能根据同一验收集反复改规则后只报告最终成功率。
跨模型阶段建议覆盖至少两个供应商的模型，并在可获得时加入本地模型；缺少的组合明确标注“未测”。
关键约束在验收样例中不允许因压缩发生已知违反；出现违反的配置先停止自动采用候选，修复后重跑相关类别。
不同任务可有不同收益阈值，必须预先记录。不要用某个总体平均节省率掩盖特定领域的语义退化。

## 12. 研究依据及适用边界

- [tiktoken 官方仓库](https://github.com/openai/tiktoken)：支持按具体编码计数。其 BPE 行为说明字符数、字节数和 token 数不能互相替代；本项目仍需对目标编码实际测量。
- [MetaGlyph：Semantic Compression of LLM Instructions via Symbolic Metalanguages，v1](https://arxiv.org/html/2601.07354v1)：研究借助预训练中已有的符号含义、无需图例的指令压缩。不同模型和算子的表现差异明显；§4.4 使用空白分词计数，报告比例不能直接当作 API tokenizer 节省率；§7.3 未证明系统级延迟改善或其他模型泛化。
- [Telegraph English：Semantic Prompt Compression via Structured Symbolic Rewriting，v1](https://arxiv.org/html/2605.04426v1)：提供按原子事实改写和显式关系表达的思路。§4.2 使用 `cl100k_base`，包含短文本膨胀；§8 说明英文、同厂商闭源评估模型、生成问答偏差及编译成本等限制，不能据此推定中文或本地模型有相同收益。

这些来源支持开展受控实验，也提示必须保留模型、语言、计数方法和任务边界。本文的架构、示例与验收门槛是本项目的设计选择，不是上述论文已经替本项目验证的结果。
